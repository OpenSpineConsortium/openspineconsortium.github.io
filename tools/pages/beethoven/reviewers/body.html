Beethoven

For reviewers and security offices

Beethoven is a browser extension that starts, watches and stops a Claude Code worker in your own account on your university's cluster, through the Open OnDemand portal you already use. When the worker connects, it hands you the link that opens that session at claude.ai and in the Claude app. It talks to one website, your portal: it holds no site permission on claude.ai and never asks for one, never sees your Claude sign-in, and runs no code it did not ship with.

What it never does

  • Beethoven has no site permission on claude.ai or any Anthropic page and never asks for one. It does not run on those sites, does not read them and does not change them; a click on its button on such a tab reads only the tab's address, to refuse it. It opens an Anthropic page in a new tab in two cases (the sign-in page Claude Code printed during a sitting you started; your session's claude.ai/code link when your worker connects) and the connectors settings page for the optional Google Drive step, as a bookmark would; nothing of the extension runs there.
  • Beethoven never sees your Claude sign-in. You sign in to Claude Code yourself, on Anthropic's own page; the one-time code you paste into the extension's box is typed once into your own job's terminal on your cluster and is not stored, not logged and not sent anywhere else; the extension reads only whether Claude Code says it is signed in.
  • Beethoven runs no code it did not ship with. Its daily update check fetches a signed list, not a program.
  • Beethoven works with one website: the Open OnDemand portal you connect. It requests access to that site, and to nothing else, only from a click: its icon on that site's tab, a Connect or Allow button in its panel, or Connect on its setup page, where you can type the site's address. It refuses an address on claude.ai, claude.com or anthropic.com before asking the browser for anything. Its only other requests go to the maintainer: the approval check, which sends the account name your portal shows for you, your portal's address, the product name and its version, and the installation identifier (a random number the extension makes when its agreement is accepted, not derived from the device), so the maintainer's access service can answer whether that account is approved on this installation; and a daily fetch, from the maintainer's website, of that service's address and the signed list of withdrawn versions, which carries nothing about you.
  • Beethoven does not read your portal cookie and does not sign in for you. When your portal asks for a sign-in, the extension asks you to sign in in a tab. There is no licence key: your institution's own sign-in identifies you, and the only thing you paste is the one-time code Claude Code's own sign-in gives you, which goes to your own job.
  • Beethoven sends its maintainer no usage data, no error reports and no activation request; the approval check is the only thing it sends about you. Its audit log of what it asked your portal never contains what you typed to sign in and is never transmitted.

Permissions and code

Permissions: storage, alarms, scripting, activeTab and sidePanel. One optional host permission, https://*/*, which the extension asks your browser to grant for the one portal website you click from or type on its setup page, and it refuses to work until that is granted; no host permission at install time, and none on any Anthropic domain: it refuses an address on claude.ai, claude.com or anthropic.com before asking for anything. Never requested: cookies, tabs, webRequest, webRequestBlocking, declarativeNetRequest, nativeMessaging, debugger, identity, clipboardRead.

No remote code: the daily update check fetches one signed list (killlist.json) and checks its signature against a key built into the extension; the list can withdraw a version and nothing else. No licence key: the one request that carries anything about the person is the approval check, which sends the account name the portal shows, the portal's hostname, the product, the version and the installation identifier to the maintainer's access service (beethoven-access.openspineconsortium.workers.dev, named in services.json) and is answered yes or no. The bundle is minified for size and not obfuscated. Security reports go to the notice address on the support page.

Distribution and installations

Beethoven is published only as a private listing in the Chrome Web Store: the listing opens for the Google accounts in the lab's group of testers, which the maintainer adds one by one after approving a request. There is no public listing, no other store and no download from this site. The access service ties each approved account to one installation, identified by the random installation identifier the extension makes when its agreement is accepted and keeps in its own storage (it is not derived from the device, and a reinstall makes a new one). A check from a second installation of the same account is refused, and the maintainer is told; the maintainer can move the approval or withdraw it. The service keeps the identifier and when it was first and last seen; of refused checks it keeps a count, the time of the last one and the first eight characters of a one-way hash of the refused installation's identifier. This is an access rule the extension and the service keep between them, not copy protection: it makes casual sharing fail, and the agreement makes sharing a breach.

Beethoven's use of information received from your browser complies with the Chrome Web Store User Data Policy, including the Limited Use requirements.
