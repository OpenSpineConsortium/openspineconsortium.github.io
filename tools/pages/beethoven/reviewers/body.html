Beethoven

For reviewers and security offices

Beethoven is a browser extension that starts, watches and stops a Claude Code worker in your own account on your university's cluster. When the worker connects, it hands you the link that opens that session at claude.ai and in the Claude app. It reaches the cluster in one of two ways: directly over ssh to the cluster's login node, through a small helper you install from inside the extension (no VPN), or through the Open OnDemand portal you already use. It holds no site permission on claude.ai and never asks for one, never sees your Claude sign-in, never keeps your cluster password or code, and runs no code it did not ship with.

What it never does

  • Beethoven has no site permission on claude.ai or any Anthropic page and never asks for one. It does not run on those sites, does not read them and does not change them. It opens an Anthropic page in a new tab only as a bookmark would (the sign-in page Claude Code printed during a sitting you started, your session's claude.ai/code link, the connectors settings page for the optional Google Drive step, the plans page); nothing of the extension runs there.
  • Beethoven never sees your Claude sign-in. You sign in to Claude Code yourself, on Anthropic's own page; the one-time code you paste into the extension's box is typed once into your own job's terminal on your cluster and is not stored, not logged and not sent anywhere else.
  • Beethoven never keeps your cluster password or verification code. On the direct way you type them into its own sign-in sheet once; it sends them only to your cluster, inside the encrypted ssh session, after the cluster's host key matched the one it carries, and never stores, logs or sends them to its maintainer. On the portal path you type them into your browser's or your portal's own pages, which it never reads.
  • Beethoven's key in your browser can never sign a worker in to Claude, open a terminal, transfer files or forward ports: its one line in your cluster account forces every use through a gate with eight fixed commands. Protecting it with Windows Hello or Touch ID is optional; Forget this computer removes it and its line.
  • Beethoven's helper, which you install from inside the extension, connects only to your cluster's ssh port, holds no credential, keeps no log of what it carries and sends nothing to the maintainer.
  • Beethoven runs no code it did not ship with. Its daily update check fetches a signed list, not a program.
  • Beethoven asks for a website only from a click, one at a time: your university's Open OnDemand portal. It refuses an address on claude.ai, claude.com or anthropic.com before asking the browser for anything. Its only other requests go to the maintainer: the approval check (the account name your cluster accepted, your portal's address, the product name and its version, and the installation identifier, a random number made when its agreement is accepted, not derived from the device), sent only after your cluster accepted your sign-in; and a daily fetch of the service's address and the signed list of withdrawn versions, which carries nothing about you.
  • Beethoven sends its maintainer no usage data, no error reports and no activation request; the approval check is the only thing it sends about you. Its audit log never contains what you typed to sign in and is never transmitted.

Permissions and code

Permissions: storage, alarms, scripting, sidePanel and nativeMessaging. One optional host permission, https://*/*, which the extension asks your browser to grant for the one portal website, only inside a click (Agree and continue on its welcome page, Allow again in its panel, Change in its Settings); no host permission at install time, and none on any Anthropic domain: it refuses an address on claude.ai, claude.com or anthropic.com before asking for anything. Never requested: activeTab, cookies, tabs, webRequest, webRequestBlocking, declarativeNetRequest, debugger, identity, clipboardRead.

nativeMessaging reaches only the extension's own helper: Chrome lets an extension talk to a program on the computer only when that program has registered itself for that extension, and the helper exists only after the user saved and ran its installer, which is a file inside the extension's package. scripting loads the extension's page script only into a tab it opened itself on the granted portal; no page script is registered.

No remote code: the daily update check fetches one signed list (killlist.json) and checks its signature against a key built into the extension; the list can withdraw a version and nothing else. No licence key: the one request that carries anything about the person is the approval check, which sends the account name the cluster accepted, the portal's hostname, the product, the version and the installation identifier to the maintainer's access service (beethoven-access.openspineconsortium.workers.dev, named in services.json) and is answered yes or no. The bundle is minified for size and not obfuscated. Security reports go to the notice address on the support page.

The direct way: the helper, the sign-in and the key

The helper. A browser extension has no raw sockets, so the direct way uses a native messaging host (com.openspineconsortium.beethoven.bridge) that ships inside the package as a plain script: Windows PowerShell behind a .cmd launcher on Windows, Perl on macOS and Linux (Python 3 where Perl is absent). The user installs it once, in their own user account, with no administrator rights; the page that offers it writes the extension's own ID into the copy it saves, so the host's registration names only that extension. It opens TCP only to the addresses on its allowlist (grid.wayne.edu:22, built in), carries base64 bytes both ways, never logs them, holds no credential, has no shell, starts no other program and exits when Chrome closes it. It is unsigned, so the operating system warns the first time it is opened.

The sign-in. The extension's own ssh client (WebCrypto, no third-party code) checks the server's host key against the fingerprint the site profile carries before it sends anything. The first sign-in uses the cluster's own keyboard-interactive prompts (the password, then the Google Authenticator code), which the user answers in the extension's own sign-in sheet; the answers are held in memory only until they are sent into the session, and are dropped once sent: never stored, logged or offered to be remembered. After three refusals in a row the extension stops and asks the cluster nothing more for that account for fifteen minutes, so the account is not locked. The signed-in session of a first sign-in is held, in memory, for up to ten minutes, so the user's first Claude sign-in can run in it.

The key. In that session the extension makes a key in the browser (kept in the extension's IndexedDB, wrapped by a non-extractable browser key kept beside it, or by a key derived from the user's passkey if the user opts in to Windows Hello or Touch ID; the signing key is always used non-extractable, in memory) and adds one line to the user's ~/.ssh/authorized_keys: restrict,command="<the lab's shared copy>/bin/hpcworker gate" <key> beethoven-browser <date>. The gate accepts eight fixed verbs (version, status, watch, connect, stop, restrict, read of four named run files, forget), refuses any other character or word, caps each key at three worker names in any seven days, twelve starts an hour and two watches at once, and starts a worker only with --login never: the key can never run the Claude sign-in. The gate, and everything the extension runs on the login node, is bash with coreutils, grep, sed and awk; no Python. The cluster-side tool refuses to add a key unless the lab's shared copy, and every folder above it, can be changed by its owner alone, since every key's forced command runs that copy. Forget this computer deletes the key and, through the gate, the line; withdrawing a user's approval does not remove the line. A relay server is used only if a university's site profile names one; none does, and the privacy statement would name it first. No other extension can serve as the bridge: Chromium allows sockets to Google's Secure Shell alone, and it offers other extensions none.

Distribution and installations

Beethoven is published only as a private listing in the Chrome Web Store: the listing opens for the Google accounts in the lab's group of testers, which the maintainer adds one by one after approving a request. There is no public listing, no other store and no download from this site: the helper's installers are files inside the extension's package. The access service ties each approved account to one installation, identified by the random installation identifier the extension makes when its agreement is accepted and keeps in its own storage (it is not derived from the device, and a reinstall makes a new one). A check from a second installation of the same account is refused, and the maintainer is told; the maintainer can move the approval or withdraw it. The service keeps the identifier and when it was first and last seen; of refused checks it keeps a count, the time of the last one and the first eight characters of a one-way hash of the refused installation's identifier. This is an access rule the extension and the service keep between them, not copy protection: it makes casual sharing fail, and the agreement makes sharing a breach.

Beethoven's use of information received from your browser complies with the Chrome Web Store User Data Policy, including the Limited Use requirements.
