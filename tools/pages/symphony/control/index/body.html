Symphony control panel

Sign in to take the controls

One press: GitHub asks, the first time only, whether SymphonyBoard may act as you, and sends you straight back here signed in. The token GitHub issues is kept only in this browser, lasts eight hours at a time (the page renews it as you go), and reaches only the repositories SymphonyBoard is installed on, within the App’s permissions and your own access; a small stateless service turns GitHub’s one-time code into that token and keeps nothing.

Sign in with GitHub switches on once its sign-in service is running; until then, use a token below.

Use a fine-grained token instead Make one at github.com/settings/personal-access-tokens/new: name it, pick the repositories Symphony runs in under Repository access, and under Repository permissions set Actions to Read and write (read lists the runs, write starts a workflow), Checks to Read-only, Contents to Read and write (the read shows the board and the Claude accounts’ readings, the write merges a pull request), Issues to Read and write and Pull requests to Read and write; Metadata comes with them. Adding a Claude account also needs the organization permissions Secrets and Variables set to Read and write. Tracking a drive on the Folders tab also needs the repository permission Secrets set to Read and write. Press Generate token and paste it here. The token is used for GitHub’s API from this browser only; nothing of this site ever receives it. For an organization’s repositories the organization must allow fine-grained tokens (its Settings, Third-party access, Personal access tokens). This is a GitHub token; Claude tokens are made under the Tokens tab’s + Add Token, and the page never sees one.

Board

What this is

The file STATE.md on the branch board, as the board workflow last wrote it: the claims, the open pull requests, the overlaps, the queue, the issues given to workers and the blockers, and, once the repository’s protocol draws them, the dependency charts, which this tab draws in place, each node coloured and edged by its state as the Dependencies tab’s key shows. Rewrite the board from the Command tab to have it read again.

Tasks

How tasks work

The open issues by the protocol’s labels. An issue labelled todo and held by nobody is free for any session or worker to claim; one a worker’s label names waits for that worker; a claim is a branch claude/N. + Add task queues one for the workers, or hands it to @claude at once. Press a card for where it stands, its gear to give it to a worker or ask Claude on it, its × to close it. Open the Task form on GitHub for the same with GitHub’s own page.

What the charts show and read

Each open epic’s tasks and what blocks them, drawn as a chart, with the goals above their epics: the same chart the board writes into STATE.md once the repository’s protocol is new enough to draw it, and the Board tab draws that one in place, as long as it is a chart as the board writes it (any other block there is shown as text and never drawn); until then this tab is the only place it is drawn. A task is a sub-issue of the epic on GitHub, and what blocks it is GitHub’s own blocked-by relation, both set on the issue’s page under Sub-issues and Relationships; a goal is an issue labelled goal whose sub-issues are epics. An arrow runs from the issue that blocks to the issue it blocks, dotted once the blocker is closed, and a thick one from a goal to each of its epics; a node’s colour and edge are its state (green to do, amber and dotted claimed, blue on a lit fill in review, red and thick blocked, grey, dashed and struck through closed, and a thin pale edge open, an issue in none of those states), so no two states differ by colour alone, as the key above the charts shows, and an epic’s card counts its closed tasks with a bar and its tasks by state, its sub-issues in another repository, which the bar counts and the chart does not draw, and the blockers from outside the epic each counted apart.

Where there is more than one chart, a tile for each above them, All, Goals and every epic, with a bar of its issues by state, shows one chart at a time, or every one for All; an epic’s tile says how many of its tasks are closed, the Goals tile how many issues its chart holds and All how many charts there are. The tiles are one row, which scrolls sideways, by the mouse’s wheel too, where they run past its end; the left and right arrow keys, Home and End move from tile to tile, Previous and Next at the top of a card step to the chart beside it, and the one you last chose is kept in this browser, for this repository. A chart wider than its card is dragged with the mouse like a map, or drawn whole at the card’s width with Fit and pressed again for its own size. Under each chart its list says the same in words, folded until you open it, and open by itself where the chart cannot be drawn. Clicking a node, here or in the Board tab, or pressing Centre its row, opens the Tasks tab and centres that task’s row there where the task tables hold it, as the assistant’s focus does, and opens no other page; where they do not (a closed task, a blocker from outside, a row the filter hides) this tab says why, and the message line under the console says the same either way. To draw it the page reads, as you, whenever it reads the issues and whether or not this tab is open, the sub-issues of each open issue labelled epic or goal and the issues blocking each of an epic’s sub-issues, at most sixty reads a draw and none once GitHub says the token has fewer than a hundred calls left this hour, and writes nothing; it draws again whenever the issues are read again (Refresh). The chart is drawn in this browser by a copy of Mermaid the site carries, loaded only when there is a chart to draw.

Explore

How to move through it and what it reads

The whole project as a map, one level at a time: the repository, its goals and epics, each epic’s tasks, the pull requests of a task (or its claim branch where it has none), the GitHub Actions runs on that branch, each run’s jobs, each job’s steps and, at the bottom, the lines of a step’s log, where the steps that run Claude are marked. Click a tile, or point at it and scroll up, to go into it; scroll down, press Backspace or pick a level in the trail at the top to come back out. The scroll wheel scrolls a long level as usual; a new turn of the wheel that starts at its top, over a tile, goes in, and one that starts at its bottom comes out, so reaching the end of a list never moves you by itself. The arrow keys move between tiles and Enter goes in. The outline on the left shows the levels on your way down and what sits beside each; click a name to go there.

The repository, its goals, epics and tasks come from what the console has already read (the Dependencies tab’s reads). Everything below a task is read from GitHub as you, only when you go into it: the runs on a branch, a run’s jobs and steps, and a job’s log, one read each, none once GitHub says the token has fewer than a hundred calls left this hour. What is read stays in this tab’s memory until you choose another repository, the logs of the last three jobs only, and is written nowhere; Read again reads a level or a log afresh, for a run still going. GitHub hands a job’s log over from its own storage; where your browser may not read it from there, the step says so and links the log on GitHub.

Workers

Where workers are kept

The registry under .github/symphony/workers/: each routine or worker in Actions is one file there, and a person’s sessions need none. + Add worker opens the “Add a worker” issue; its workflow checks the answers and opens the pull request that adds the file, which joins the registry when it merges. A card’s gear opens a pull request that changes its file, and its × one that removes it; neither changes anything until it merges. The same form on GitHub: Add a worker.

Agents

What an agent is

An agent is a set of instructions and the tools it may use, kept as a Claude Code subagent file under .claude/agents/ and listed in .github/symphony/agents.json with its purpose. Any session in the repository can hand it work by name; its gear runs it in GitHub Actions on a pull request or issue and sets the tokens it runs on, which is how usage is divided between review, development and testing; and coordbench and flowbench measure the same file. + Import agent brings one in from another repository or an address by pull request, so it joins only once someone merges it; its × opens the pull request that removes it.

Folders

How the drive is kept in step

A repository that tracks files and folders of your OneDrive, one press per step, in the column beside the list. From Track on, the repository’s own workflow, drive-sync.yml, brings what changed in the drive down as a pull request every half hour and sends what changed in the repository back up, and a new comment in a document becomes a task on the board. On a private repository each of those half-hourly runs spends at least a minute of the account’s Actions minutes, about 1,440 a month of GitHub Free’s 2,000 (3,000 on Pro and Team), from the day the repository is made, whether or not it tracks a drive; a public repository spends none. Google Drive comes later, once there is a way that needs no key: Google’s own picker takes a browser API key, which the owner has declined.

Connect: Microsoft asks, on its own page, whether Symphony may read and write your files and keep that access when you are away, and sends you straight back to this tab. A personal OneDrive connects at once; a work or school account may need its organization’s IT department to approve Symphony first, and Microsoft says so on its page. The page then holds the drive’s two tokens in its memory alone, never in the browser’s storage, so finish the steps in one sitting: a reload, signing out or a sign-in as another GitHub account forgets them, and Connect is one press again. Leaving the page for Microsoft also ends the renewals of a sign-in with GitHub made for this tab alone, whose token still serves for the rest of its eight hours.

The list: your OneDrive, drawn here from Microsoft Graph as you, in this browser, as a file explorer: the folder tree on the left, Back, Forward and Up beside the address, Details or Large icons at the foot, and a search box for the folder shown. Double-click a Word, Excel or PowerPoint file to open it in that program on your computer, where your edits save straight to the drive (your browser may ask first); any other file opens on OneDrive’s own page, and a right click offers both and Tick. Tick in it what to track. The page draws it itself rather than opening OneDrive’s own picker, since the access you gave reaches every file already and the picker would need a token for your tenant’s SharePoint, a page of Microsoft’s inside this one and an address that differs between a personal and a work account. A ticked folder is tracked with everything in it, six levels down. Nothing of the list leaves this browser but the names and ids of what you tick, which go into the repository’s file.

The repository: GitHub’s own form makes it from the template, named by you, so its first commit stays yours and no App needs to administer it. While the template is internal to OpenSpineConsortium’s enterprise, that form works only for the enterprise’s members; anyone else makes the repository through the front door: install SymphonyBoard and press Create on the form its install leads to, which brings a new or empty repository the whole template, drive-sync.yml with it, by a pull request to merge. The form opens in a new tab; name the repository, press “Create repository”, come back here and press “Find the repository I just made”, which lists it in the bar’s Repository and chooses it. Signed in with GitHub, the page reaches it once SymphonyBoard is installed on it (an installation on all your repositories covers it); a fine-grained token reaches what it was made for, and Track needs it to hold Contents, Secrets and Actions, each Read and write.

Track writes three things, as you: the drive’s refresh token, sealed in this browser with the repository’s public key the way GitHub’s own secrets page seals one, as the secret SYMPHONY_DRIVE_REFRESH; the file .github/symphony/drive.json naming the drive, the folder and what you ticked; and the first run of the sync. The page then drops the drive’s tokens from its memory. In a public repository the files you tick, their names and the comments in them become readable by anyone, so the tab asks you to confirm before it tracks into one. Where the default branch takes only pull requests, the file waits on a pull request; until it merges, the half-hourly sync runs with the new secret on the file the default branch already holds. Whoever can run a workflow on the repository, anyone who may write to it, can read that secret and, through the sign-in service, reach every file of your OneDrive with it, not only what you ticked, until it lapses or you withdraw Symphony’s access at Microsoft: at account.live.com/consent/Manage for a personal account, or in My Apps for a work or school account, where its administrator may have to. Deleting the secret withdraws nothing at Microsoft. A Microsoft refresh token lasts 90 days, and the run cannot keep the newer one Microsoft issues on each sync, so the tab says when to press Connect OneDrive again, then Track, which replaces the secret and the date; what the repository tracks is ticked already.

    Notebooks

    What a notebook is and where these come from

    A notebook groups a few of your OneDrive’s files as one context, as NotebookLM does: the files stay where they are, a file may sit in several notebooks, and each notebook is a private repository of its own in which Claude works in the background, keeping its research, its drafts and its references beside what it reads and writing its edits to a file back as tracked changes you accept or reject in Word. Nothing a notebook does can move or lose a file.

    The cards come from the proposal the drive organizer writes, notebooks.json beside catalog.json on the chosen repository’s branch drive-catalog, read here as you; a public repository holds none, and neither does an internal one, which every member of its enterprise can read, since a notebook names a person’s files. Each card shows the notebook’s title, its repository, how many files it holds and their size, their kinds, most common first, and when the newest of them last changed, and says whether its repository is made yet. Click a card for the notebook’s summary and its files, each with its kind, its last change and a link to it on OneDrive.

    + proposes a new notebook: a title, a summary, the name of its repository and the files ticked from the catalog; a card’s gear changes one, and its × takes one out of the proposal, leaving the files on the drive. Each of those writes notebooks.json on the branch drive-catalog as you, with the files no notebook holds listed as left out and whatever else the organizer wrote kept, over the version the cards were drawn from, so a change the organizer made since is never written over: the tab reads the file again and you press again. Taking out the last notebook deletes the file, and whatever else the organizer wrote in it goes too. The repository itself is made from the proposal by the notebook skill in a Claude session, as the template’s tools/notebook.py lays it out; the card says “not found” until it exists or while this sign-in cannot reach it, and warns when it is public or internal.

    About the control panel

    Your Symphony repositories from one console: the board, the queue, the workers, the checks and the pull requests, the Claude accounts, each epic’s tasks and what blocks them drawn as a chart, and a box to ask Claude. The page talks to GitHub’s API as you, from this browser, and, only when you sign in with GitHub or open the Folders tab, to the sign-in service, and, for a drive you connect there, to Microsoft; the token stays in this browser. Every state here is written in words and every action is a button or a link with a name, so you and a browsing Claude read and drive it alike. Each tab has its own address: #command, #board, #tasks, #dependencies, #pulls, #runs, #workers, #agents, #tokens, #leaders, #share, #folders, #explore, #notebooks and #about. What it costs, against the other ways of running agents, is on the cost page.

    What this page keeps and sends

    In this browser: the GitHub token, until you press Forget the token. With Keep me signed in ticked, it is kept for every tab of this browser, beside the refresh token GitHub issued with it after Sign in with GitHub, with which the page renews the token after its eight hours. Unticked, the token is kept in this tab’s own storage, which the browser clears when the tab closes and brings back when it reopens or restores the tab, and the refresh token is held by the open page alone, never stored, so the renewals end once that page is gone (closed, reloaded, or replaced by another page such as the cost page) and that sign-in ends with its eight-hour token. Also kept: the names of the repositories you listed, the layout you set (the sizes you dragged the parts to and the text size), the plan you chose on the cost page, the number of the assistant issue the page uses in each repository, one it opened or found. Sent: requests to GitHub’s API, as you, for what the page shows and does (a question to the assistant goes as a comment on that issue, and the page reads the issue’s comments every few seconds while it waits for the answer; for the Dependencies tab the page reads the sub-issues of each open epic or goal and the issues blocking each of an epic’s sub-issues, draws them in this browser with a copy of Mermaid loaded from this site only when there is a chart to draw, as it draws the board’s own charts in the Board tab, and stores nothing of them: the chart is gone with the page), and nothing to anyone else, a token you paste included, which GitHub is asked about before the page keeps it; on the Folders tab, what it sends for a drive (below); on the Notebooks tab, reads of notebooks.json and catalog.json on the repository’s branch drive-catalog and of whether each notebook’s repository exists and is private, and, when you propose, change or take out a notebook, a write of notebooks.json there, all sent to GitHub as you; on the Share tab, reads of who has access and which invitations wait, an invitation to the GitHub user you name and, when you press a person’s gear or ×, a new role, a removal or a withdrawn invitation, all sent to GitHub as you, and an address you type to GitHub’s user search to find that user, while its mail buttons open Gmail, Outlook, your email app or your device’s share sheet with a note you send yourself; with Sign in with GitHub, GitHub’s one-time code to the sign-in service, which answers with the token and keeps nothing, the refresh token to the same service when the token is renewed, and a sign-in’s token once more when you press Forget the token, or sign in or paste a token GitHub accepts over it, so that GitHub revokes it; and signing in by code (in the Home Screen app, or with Sign in with a code instead), a request to the same service for a code, which it asks GitHub for with SymphonyBoard’s client id alone, then the device code GitHub gave with it, held in the open page’s memory alone and sent to the same service every five seconds, or more slowly when GitHub asks, until you have typed the short code on GitHub’s page and GitHub answers with the token, GitHub refuses, the code runs out, or you press Cancel, sign in another way or forget the token, and a token GitHub gives for a code the page has let go of once more, so that GitHub revokes it; Copy it and open GitHub puts the short code on your device’s clipboard, for you to paste on GitHub’s page. The developer receives nothing from this page. The Apps’ privacy statement, which covers it, is at /symphony/apps-privacy.html.

    On the Folders tab, in this tab’s own storage while the browser is at Microsoft, and forgotten on its return: a one-time value, a one-time secret, the panel’s query (the repository it showed) and the GitHub login the panel names. In the open page’s memory alone, until Track has written the secret and the file, Forget the token or any other sign-out, a sign-in as another GitHub account, or a reload or leaving the page: the drive’s access token and refresh token. Sent: when the tab first opens, a question to the sign-in service about which drives it is set up for, answered with a public client id; Microsoft’s one-time code to the sign-in service, which adds the client secret it holds, answers with the two tokens and keeps nothing; the refresh token to the same service when the access token runs out during a sitting; requests to Microsoft Graph, as you, for the drive’s type, its owner’s name and its id and for the list you browse; and to GitHub’s API, as you, a read of the names at the top of the default branch, so that no folder the repository already holds there is tracked into, then the sealed secret, the file (on the default branch or, where that takes only pull requests, on the branch symphony/drive with a pull request) and the request to run the sync. The repository’s own run then trades the secret for an access token at the same service on every sync; whoever can run a workflow on the repository can do the same with it, until it lapses or you withdraw Symphony’s access at Microsoft. The developer receives nothing from this tab either.
